# ตรวจทานข้อมูล Garmin กับของจริง — เช็คลิสต์รายเดือน

> ทำไมต้องมี: ระบบอัตโนมัติทั้งหมด (sanity check / drift check / reconcile) เช็คแค่ว่า
> "ข้อมูลในตัวมันเองสมเหตุสมผลไหม" (internal consistency) — **ไม่เคยเทียบว่าตรงกับตัวเลข
> จริงในแอป Garmin Connect ไหม** (external validation). สองอย่างนี้ต่างกัน. การสุ่มเทียบ
> มือเดือนละครั้งคือด่านสุดท้ายที่จับได้ว่า parser แปลงหน่วยผิด / หยิบ field ผิด / API เพี้ยน
> แบบที่ระบบอัตโนมัติมองไม่เห็น.

## ทำเดือนละครั้งพอ (ไม่ต้องทุกวัน) — ใช้เวลา ~10 นาที

เลือกนักกีฬา 1 คน + กิจกรรมวิ่ง 1 รายการในเดือนนั้น (สุ่ม ไม่ต้องเลือกที่ดูปกติ) แล้วเทียบ:

### 1. เปิดตัวเลขจากระบบ

เปิด dashboard (`run_dashboard.bat`) → เลือกนักกีฬาใน sidebar → แท็บ **📉 Splits** เลือกกิจกรรมนั้น
(ค่า wellness ของวันเดียวกันดูที่แท็บ **💤 Health**)

> อยากได้ค่าดิบที่ dashboard ไม่ได้โชว์ ให้ query `garmin.db` ตรง — `WHERE deleted_at IS NULL`
> ใช้กับ `fact_activity`/สถิติกิจกรรม; ตาราง wellness ไม่มี soft-delete
> ```
> garmin\.venv\Scripts\python.exe -c "import sqlite3;c=sqlite3.connect('garmin/data/garmin.db');..."
> ```

### 2. เปิดกิจกรรมเดียวกันในแอป Garmin Connect (มือถือ/เว็บ) แล้วเทียบทีละค่า

### 3. เทียบ wellness ของวันเดียวกัน (ในแอป: Sleep / Body Battery / HRV / Readiness)

เลือก **วันที่จบแล้ว** อย่างน้อย 1 วัน และจดวันที่/ความสดที่ dashboard กำกับไว้ด้วย. Body Battery
"ตอนนี้/ล่าสุด" บนหน้า Today/Team เป็นคนละค่ากับ high/low รายวันบนหน้า Health. ค่าเฉลี่ย 30/90 วัน
ต้องดู **จำนวนวันที่มีข้อมูลจริง/denominator** คู่กันเสมอ; ระบบข้าม NULL. Sleep/RHR รวมค่าของวันนี้ได้
เมื่อสรุปหลังจบคืนแล้ว ส่วน BB-high/Stress และค่า intraday อื่นไม่นับวันนี้ที่ยังไม่จบ

| ค่า | ระบบ | Garmin Connect | ตรงไหม |
|---|---|---|---|
| Resting HR | | | ☐ |
| Sleep score | | | ☐ |
| Body Battery (สูง/ต่ำ) | | | ☐ |
| HRV คืนล่าสุด | | | ☐ |
| Sleep respiration | | | ☐ |
| Training Readiness + เวลาของ snapshot | | | ☐ |
| Recovery Time (ชั่วโมง/นาที) | | | ☐ |

ถ้าอุปกรณ์ไม่มี Training Readiness ให้จดว่า "ไม่รองรับ/endpoint ไม่ส่ง" แทนการใส่ 0; ตรวจรุ่นที่ระบบรู้จัก
จาก `dim_athlete_device` และดูประวัติทั้งฐาน ไม่สรุปจากช่วงวันที่เลือกอย่างเดียว. Recovery Time ต้นทางเป็น
**นาที** (`recovery_time_min`): เช่น 5,425 นาที = 90 ชม. 25 นาที ไม่ใช่ 5,425 ชั่วโมง

### 4. รัน data-quality check แล้วเก็บผลไว้กับบันทึกเดือนนั้น

```powershell
garmin\.venv\Scripts\python.exe garmin\scripts\check_drift.py
garmin\.venv\Scripts\python.exe garmin\scripts\check_drift.py --json
```

ผลจะแสดง coverage ต่อ field สำหรับ 7 วันและ 30 วันเต็มล่าสุดโดยนับวันปฏิทินที่แถวหาย/ว่างใน denominator,
จับทั้ง snapshot หายทั้งวัน, partial snapshot และค่าผิดช่วง/ความสัมพันธ์ (เช่น Body Battery high < low).
`--json` เป็น strict JSON เหมาะกับเก็บเป็นหลักฐานหรือส่งต่อ
ให้เครื่องมืออื่น; exit code 1 หมายถึง "มีจุดให้ตรวจ" ไม่ได้แปลว่าควรแก้ DB โดยไม่เทียบ Garmin ก่อน

## ถ้าเจอไม่ตรง

- **หน่วยเพี้ยนเป็นเท่าตัว** (เช่น เพซ ×10, น้ำหนัก ×1000) → parser แปลงหน่วยผิด ดูจุดแปลง
  ใน `03_backfill.py` (เคยเจอ: LT speed สเกล 0.1 m/s, weight เป็นกรัม)
- **ค่าเป็น NULL ทั้งที่แอปมี** → ดูวันที่/ความสดและ log ก่อน; fast wellness จะย้อนซ่อม partial ของเมื่อวาน
  โดยพักอย่างน้อย 6 ชม. ระหว่างครั้ง. ถ้ายังขาดให้รัน `check_drift.py`, เทียบ Cloud และค่อยแยกว่า
  endpoint มาช้า / อุปกรณ์ไม่ส่ง / parser เปลี่ยนชื่อ field — อย่าเติมค่าหรือแก้ key จากการเดา
- **ค่าดีเดิมกลายเป็น NULL หลัง sync** → ถือเป็น regression เพราะทั้ง fast และ full/deep ต้อง merge
  เฉพาะ field ที่ API ส่งค่าจริง; `fetched_at` เป็นเวลา UTC ระดับแถวและไม่ยืนยันว่าทุก field สดพร้อมกัน
- **Readiness ดูไม่ใช่ค่าล่าสุด** → เทียบ timestamp ของ snapshot ไม่ใช่ตำแหน่งใน list; ระบบต้องเลือก
  snapshot ที่ timestamp ล่าสุดและเก็บ input context/feedback ไว้ตรวจย้อน
- **Recovery Time มากผิดธรรมชาติ ~60 เท่า** → ตรวจว่ากำลังอ่าน `recovery_time_min` และแปลงนาที
  เป็นชั่วโมง+นาที; คอลัมน์ `recovery_time_hrs` เป็น legacy ที่ชื่อผิดและเก็บค่าดิบนาที
- **กิจกรรมมีในแอปแต่ไม่มีในระบบ** → ยังไม่ถูกดึง (เช็ค log / รัน backfill วันนั้นซ้ำ)
- **กิจกรรมมีในระบบแต่ลบไปแล้วในแอป** → รอ reconcile รายสัปดาห์จับ หรือรันมือ:
  `fetch_all.py --days 90 --reconcile`
